# 04. 웹 아키텍처

## 결정: Next.js (정적 export)
React 단독(Vite SPA)과 Next.js 중 **Next.js**를 선택한다.

| 기준 | React (Vite SPA) | Next.js (static export) |
|---|---|---|
| 검색 노출 | URL 하나, 메타태그 공통. 선수별 페이지가 색인되기 어렵다 | 선수·구단마다 고유 URL과 `<title>`/OG 태그가 빌드 시 HTML에 박힌다 |
| 데이터 주입 | 클라이언트에서 JSON fetch | 빌드 시 JSON을 읽어 HTML에 포함. 첫 화면이 바로 뜬다 |
| 라우팅 | react-router 별도 설정 | 파일 기반 (`app/player/[id]/page.tsx`) |
| 서버 필요 | 없음 | **없음** (`output: 'export'` 로 순수 정적 파일) |
| OG 이미지 | 직접 생성 파이프라인 필요 | `opengraph-image.tsx` 로 선수별 공유 이미지 자동 생성 |

핵심은 "Next.js = 서버"가 아니라는 점이다. 정적 export 모드에서는 빌드 결과가 HTML/JS/CSS 파일뿐이라 React SPA와 배포 비용이 같고, 검색 노출만 얻는다. Supabase가 일시정지돼도 사이트는 영향이 없다.

(참고: 콘텐츠 중심 정적 사이트라면 Astro도 적합하지만, 이미 Next.js 쪽으로 기울어 있고 생태계가 넓어 Next.js로 간다.)

## 스택
| 역할 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | Next.js 15 (App Router) + React 19 + TypeScript | `output: 'export'`, `images.unoptimized: true` |
| 스타일 | Tailwind CSS 4 | 부상 색상은 CSS 변수(`--inj-1/2/3`)로만 정의, 다크모드는 `prefers-color-scheme` |
| 폰트 | Pretendard (jsdelivr CDN), 숫자 `tabular-nums` | |
| 신체 지도 | 자체 인라인 SVG 컴포넌트 | 라이브러리 없음. zone path는 `data-zone` 속성으로 DB `svg_zone` 과 매핑 |
| 차트 | Recharts | 타임라인(선수), 구단별 결장일 막대(리그) |
| 상태 관리 | 없음 (URL 쿼리로 필터 표현) | 정적 데이터라 전역 상태 불필요 |
| 테스트 | Vitest | IAI 계산·색상 등급 함수 단위 테스트만 |
| 배포 | Vercel Hobby (1순위) / GitHub Pages + Actions (2순위) | 둘 다 무료. GitHub Pages는 `basePath` 설정 필요 |

## 데이터 흐름
```
Supabase ─▶ crawler/export-json.js ─▶ web/data/*.json (커밋 대상)
                                          │  빌드 시 fs 로 읽음
                                          ▼
                          generateStaticParams + page.tsx ─▶ out/ (정적 HTML)
```
- `export-json.js` 출력 경로를 `web/public/data/` 에서 **`web/data/`** 로 바꾼다. 브라우저가 fetch하는 게 아니라 빌드 시 읽어 HTML에 넣기 위해서다. 공개 노출되는 원본 JSON이 없어져 저작권·약관 측면에서도 낫다.
- `web/data/` 는 커밋한다. 데이터 갱신 = export 실행 → 커밋 → 배포.
- JSON 스키마 (export-json.js 와 동일):
  - `meta.json` — teams, body_parts, settings
  - `ranking.json` — 선수별 IAI 집계
  - `league_parts.json` — 부위별 리그 합계
  - `players/{id}.json` — 선수 상세 (parts, injuries, articles: title/press/url/date 만)

## 라우트
| 경로 | 내용 | 메타 |
|---|---|---|
| `/` | 리그 요약 + IAI 랭킹 + 리그 신체 히트맵 + 구단별 막대 | 기본 OG |
| `/team/[id]` | 선수 카드 그리드(소형 신체 SVG + IAI), 정렬 | "삼성 라이온즈 부상 이탈 현황 2021–2026" |
| `/player/[id]` | 신체 SVG 앞/뒤 + 부위 칩 + 타임라인 + 근거 기사 | `generateMetadata` 로 선수명·요약, `opengraph-image.tsx` 로 신체 지도 이미지 |
| `/about` | 방법론(IAI 공식·색상 기준), 데이터 출처, 한계, 면책, 정정 요청 경로 | |
| `sitemap.xml`, `robots.txt` | `app/sitemap.ts`, `app/robots.ts` | 정적 export 지원 |

MVP 1차는 삼성만 있으므로 `/` 는 사실상 삼성 페이지와 같다. 라우트 구조는 처음부터 다구단 기준으로 두고 데이터만 1개 구단으로 시작한다.

## 검색 노출 (SEO) 체크리스트
- 페이지마다 `generateMetadata` 로 title/description/OG/Twitter 카드
- 선수 페이지 `opengraph-image.tsx` 로 신체 지도 PNG 자동 생성 → 공유 시 썸네일
- `sitemap.ts` 에 전 선수·구단 URL 포함, `robots.ts` 허용
- 선수명·구단명·"부상"·"이탈" 등이 HTML 본문에 텍스트로 존재 (SVG 안 숫자도 `<text>`)
- 사이트 이름 일관(`KBO 부상 이탈 트래커`), 기본 라벨은 중립 표현

## 공개 시 표현·법적 원칙 (02-아키텍처 "데이터 이용 조건" 참고)
- 기사 요약·본문 노출 금지. 제목 + 언론사 + 날짜 + 원문 링크만.
- 지표 라벨은 "부상 이탈 지수(IAI)" 하나로 통일. 조롱성 별칭은 두지 않는다.
- 모든 수치 옆에 근거 기사, `/about` 에 방법론·한계·면책·정정 요청 연락처.
- 구단 로고·선수 사진 사용 안 함.

## 구현 순서 (디자인 확정 후)
1. `create-next-app` + Tailwind + static export 설정, `web/data/` 샘플 JSON으로 빌드 확인
2. `BodyMap.tsx` — zone path 그리기, 색상 등급 함수, 라벨
3. `/player/[id]` — BodyMap + 타임라인 + 기사
4. `/`, `/team/[id]` — 랭킹·카드
5. 메타데이터·OG 이미지·sitemap
6. `/about`
7. Vercel 연결
