# 02. 아키텍처

## 전체 흐름
```
[네이버 뉴스 검색 API] ──┐
                        ├─▶ crawler/ (Node.js) ─▶ Supabase (Postgres, 클라우드)
[KBO 엔트리 등록/말소] ──┘                              │
                                                      ▼
                                             export-json.js ─▶ web/public/data/*.json
                                                      │
                                                      ▼
                                            web/ (Next.js, 정적 빌드) ─▶ SVG 신체 히트맵 대시보드
```

## 데이터베이스: Supabase (결정 2026-10-26)
- **원본 저장소는 Supabase 무료 플랜(Postgres)** 을 쓴다. 수집·파싱·검수 결과가 모두 여기에 쌓인다.
- 무료 한도: DB 500 MB, 디스크 2 GB, 프로젝트 2개. 삼성 1개 구단(2021–2026)은 20–40 MB, 10개 구단 전체도 200–400 MB로 한도 안이다. 용량의 대부분은 `articles` 이므로 전체 리그 확장 시 부상과 연결되지 않은 기사는 파싱 후 정리한다.
- **1주일 비활성 시 프로젝트가 자동 일시정지**된다. 그래서 대시보드는 Supabase를 직접 읽지 않고 빌드 시 JSON 스냅샷을 뽑아 정적 배포한다. Supabase가 멈춰도 사이트는 살아 있고, 다시 수집할 때 Studio에서 복구하면 된다.
- 접근 방식: 크롤러는 서비스 롤 키로 서버 측에서만 쓰기. 프론트는 DB를 직접 호출하지 않는다 (RLS 설정 불필요, egress 절약).
- 로컬 SQLite(`data/kbo_injury.db`)는 오프라인 파이프라인 테스트용으로만 남긴다. 스키마는 Postgres 기준(`db/schema.sql`)이 원본이고, SQLite 버전은 그 파생이다.

## 기술 선택과 이유
| 레이어 | 선택 | 이유 |
|---|---|---|
| 수집/파싱 | Node.js 20 (ESM) + `pg` | 프론트와 같은 언어, 내장 fetch로 API 호출 |
| 저장 | **Supabase (Postgres) 무료 플랜** | 클라우드에서 관리, Studio로 검수 편함, 용량 한도 내 (위 절 참고) |
| 프론트 | Next.js (App Router) + TypeScript, 정적 export | SVG 인라인 조작이 쉽고 Vercel/GitHub Pages 배포 무료 |
| 데이터 전달 | 빌드 시 JSON 스냅샷 | 서버 없이 동작, 로딩 빠름 |
| 차트 | 인라인 SVG (신체), Recharts (타임라인) | 신체 지도는 직접 그려야 함 |

## 파이프라인 단계 (crawler/)
1. `seed.js` — 구단·부위 사전·키워드 사전·선수 CSV를 DB에 적재
2. `fetch-news.js` — 선수별 `"선수명" 부상` 쿼리로 기사 메타(제목/요약/링크/날짜) 수집 → `articles`
3. `parse-injuries.js` — 제목+요약에서 부위·유형·날짜 추출 → `injuries` (status=`auto`)
4. `fetch-roster-moves.js` — (2차) KBO 엔트리 말소/등록 수집 → `roster_moves`
5. `reconcile.js` — (2차) 부상 ↔ 말소 기간 매칭으로 `days_out` 보정
6. `export-json.js` — 프론트용 JSON 생성

각 단계는 멱등(idempotent). 다시 돌려도 중복 삽입 없음 (URL/UNIQUE 제약).

## 데이터 모델 (요약, 전체는 db/schema.sql)
- `teams` — 10개 구단
- `players` — 선수, 구단, 포지션, KBO 선수 ID
- `body_parts` — 부위 사전 (ko/en, SVG zone id, 상체/하체/팔/다리 그룹)
- `injury_keywords` — 기사 텍스트 → 부위 매핑 키워드
- `articles` — 수집 기사 원본 (URL UNIQUE)
- `injuries` — 부상 1건 (선수, 부위, 유형, 시작/종료, 결장일, 시즌, 포스트시즌 직전 여부, 신뢰도, 검수 상태)
- `roster_moves` — 1군 등록/말소 이벤트
- `settings` — GBI 가중치 등 설정값

## 중복/오탐 처리 원칙
- 같은 선수·같은 부위·시작일 ±14일 이내 기사는 **하나의 부상 건**으로 병합
- "부상 없이", "부상 우려 없다", "복귀" 만 있는 기사는 부상 신규 생성이 아니라 기존 건의 `end_date` 후보로 사용
- 모든 자동 추출 건은 `status='auto'`, 사람이 확인하면 `confirmed`, 오탐이면 `rejected`


## 환경변수
```
NAVER_CLIENT_ID=...
NAVER_CLIENT_SECRET=...
SUPABASE_DB_URL=postgresql://postgres.[ref]:[password]@aws-0-ap-northeast-2.pooler.supabase.com:6543/postgres
DB_DRIVER=supabase   # supabase | sqlite (로컬 테스트)
```
- 네이버: https://developers.naver.com 에서 애플리케이션 등록 → "검색" API 사용 설정.
- Supabase: 프로젝트 생성(리전 서울 `ap-northeast-2`) → Settings → Database → Connection string (Transaction pooler). 서비스 롤/DB 비밀번호는 `.env`에만 두고 커밋하지 않는다.

## 선수 명단 소스 (조사 메모, 2026-10-26)
MVP 1차 대상은 삼성 라이온즈 2021–2026. 아직 수집하지 않았고 페이지 구조만 확인함.

- `koreabaseball.com/Player/Search.aspx` — ASP.NET 포스트백. `ddlTeam=SS` 로 POST하면 현재 소속 선수(1군+퓨처스) 목록이 20명/페이지로 나온다. 행에 선수명·포지션·생년월일·playerId 가 있어 `players` 테이블에 바로 넣을 수 있다. 단 **현재 소속만** 보이므로 2021–2025 사이에 떠난 선수는 빠진다.
- `koreabaseball.com/Record/Player/HitterBasic/Basic1.aspx`, `PitcherBasic/Basic1.aspx` — 시즌·팀 드롭다운이 있어 시즌별 1군 출전 선수 전원을 얻을 수 있다(2021–2026 합집합에 적합). 다만 단순 포스트백으로는 에러 페이지가 반환되어 요청 순서/추가 hidden 필드 확인이 필요하다.
- `Record/Player/HitterDetail/Basic.aspx?playerId=` — 선수 상세. 생년월일·포지션(투타) 파싱 가능.
- 대안: statiz.sporki.com 은 이 환경에서 접속되지 않았음.

권장 순서: 기록 페이지로 시즌별 명단 합집합 → 상세 페이지로 생년월일/포지션 보강 → `players` 적재. 이 단계는 MVP 1차(크롤링) 진입 시 `fetch-roster.js` 로 구현.
